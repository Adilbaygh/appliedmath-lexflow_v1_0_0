# `Data/` — instances, and where every number comes from

This folder holds every instance used by `run_analysis.py`, by the benchmark
scripts in `bench/`, by the test suite and by the desktop application. The
folder is deliberately small and fully auditable: the purpose of this file is
to state, for each instance, **which parameters come from a published source,
which were imposed by the authors, and by exactly which rule** — so that a
reader can recompute the imposed numbers instead of taking them on trust.

Two derivation scripts live in `Data/design/` and are executed by the test
suite (`tests/test_data_provenance.py`), so a mismatch between this document
and the data files breaks the build.

| File | Kind | Data origin |
|---|---|---|
| `benchmarks/chain_source_bottleneck.json` | exact unit benchmark | fully synthetic, hand-written |
| `benchmarks/star_edge_bottleneck.json` | exact unit benchmark | fully synthetic, hand-written |
| `benchmarks/tie_bottleneck.json` | exact unit benchmark | fully synthetic, hand-written |
| `benchmarks/branching_shared_edge_bottleneck.json` | exact unit benchmark | fully synthetic, hand-written |
| `benchmarks/temporal_lexicographic.json` | exact unit benchmark | fully synthetic, hand-written |
| `benchmarks/gone_abat_jap.json` | operational illustration | **mixed**: published dataset + author-imposed capacities |
| `design/greedy_lining_trap.json` | counterexample | fully synthetic, hand-written |
| `synthetic_scale_500u_1022e_4p.json` | scale benchmark | fully synthetic, generated by rule |

All numeric fields in every file are stored as **exact rational strings**
(`"3/5"`, `"86932.180615"`), never as binary floating-point literals, so the
instances are identical on every platform.

---

## 1. The five exact unit benchmarks

`chain_source_bottleneck`, `star_edge_bottleneck`, `tie_bottleneck`,
`branching_shared_edge_bottleneck` and `temporal_lexicographic` are small
hand-written instances (1–3 periods, 1–3 users) whose optimal values are known
in closed form by inspection. They exist so that the closed-form Stage-1
expression, the graph-operator/node-balance equivalence and the Stage-2 and
Stage-3 selectors can be checked against exact rational answers rather than
against another numerical solution. They make no empirical claim of any kind.

They are used in `tests/test_closed_form.py`, `tests/test_lexicographic.py`,
`tests/test_operator_balance.py` and `tests/test_matrix_and_properties.py`.

## 2. `design/greedy_lining_trap.json`

A four-node counterexample constructed by the authors to show that
single-reach lining ascent can be trapped on an ε-plateau while the joint
two-reach step strictly improves the Stage-1 guarantee (from 1/2 to 1). The
whole instance is nine numbers and is reproduced in the manuscript, so it can
be checked by hand. It is a *design* instance: it is not part of the
allocation benchmark family and is never averaged into any reported result.

## 3. `benchmarks/gone_abat_jap.json`

This is the only instance with a connection to a real irrigation system, and
it is the one that needs the most care, because it mixes published and
imposed parameters.

### 3.1 Published parameters — not modified here

Taken from the Gone Abat Jap irrigation-system dataset deposited at Mendeley
Data, **doi:10.17632/xt3gsf89n9.1** (reference [39] of the manuscript):

* the network topology — 36 nodes, 35 reaches `K1`…`K35`, rooted at the
  head gate `Of1`;
* the 20 water users `F1`…`F20` and the terminals they are attached to;
* the 16 ten-day periods `11`…`26` of the irrigation season;
* the per-period water requirement of each user (`demand`);
* the per-period head-gate inflow (`source_capacity`);
* the conveyance efficiency of each reach (`efficiency`).

### 3.2 Imposed parameters — set by the authors

The published dataset contains **no measured reach-by-reach conveyance
capacity record**. The `edge_capacity` field — all 35 × 16 = 560 values — is
therefore imposed by the authors, by the rule stated in Appendix A.4 of the
manuscript and implemented in
[`design/build_gone_abat_jap_capacities.py`](design/build_gone_abat_jap_capacities.py):

1. **Design capacities (30 reaches).** The structural reaches keep the design
   discharge of the physical canal, converted to a volume per period:
   6 048 000 m³ for the main-canal reaches, 2 592 000 m³ for `K3`, and
   1 728 000 m³ for the distributor reaches. These are far above any load and
   never bind.
2. **Five instrumented reaches.** No design figure is available for `K5`,
   `K6`, `K8`, `K11` and `K12`, so one constant per reach is imposed:

   ```
   base(e) = 21/20 · max over periods of L(e, k)
   ```

   where `L(e, k)` is the inflow that reach `e` must carry in period `k` when
   every demand of its downstream subtree is met in full — a quantity
   computed from the published demands and efficiencies alone. The factor
   21/20 makes the smallest capacity-to-load ratio outside the scarcity pairs
   of step 4 equal to exactly **1.05**.
3. **Relaxed periods.** In periods 15, 20 and 25 every capacity of steps 1
   and 2 is multiplied by 11/10.
4. **Scarcity pairs.** In nine designated (reach, period) pairs the capacity
   is overridden by `c(e, k) = 9/10 · L(e, k)`, so the reach can carry only
   90 % of its load. These nine pairs are what makes the instance a scarcity
   instance, and they are the constructed part of the experiment:

   | reach | periods |
   |---|---|
   | `K5` | 12, 15, 16 |
   | `K6` | 11, 25, 26 |
   | `K8` | 13, 17 |
   | `K12` | 14 |

All arithmetic in the derivation is exact (`fractions.Fraction`); results are
rounded half-up to the six decimals stored in the file. Running

```bash
python Data/design/build_gone_abat_jap_capacities.py --table
```

prints the capacity, the full-supply load and their ratio for each of the
five instrumented reaches in each period, and verifies that all 560 stored
values reproduce the rule.

### 3.3 How this instance may and may not be read

The instance is an **operational-assessment adaptation**, not an observed
historical scarcity record, and the manuscript labels it accordingly
(Section 4.9, "Numerical Illustration on the Gone Abat Jap Network"). The
scarcity it exhibits is imposed, so results on it illustrate what the
three-stage procedure does on a network of realistic size, topology and
efficiency structure — they are not evidence that this particular scarcity
pattern ever occurred. The evidence that the procedure's behaviour does not
depend on capacities being tied to loads comes from elsewhere: the instance
families with independently drawn capacities (Section 4.10, Table 8,
Appendix A.5) and the perturbation study (Section 4.12).

## 4. `synthetic_scale_500u_1022e_4p.json`

A purely synthetic instance — 1023 nodes, 1022 reaches, 500 users, 4 periods,
2000 active period-user records — used **only** to measure how the three-stage
procedure scales on the largest instance reported. It is generated with no
random number generator at all by
[`design/build_synthetic_scale.py`](design/build_synthetic_scale.py), which
regenerates the file byte-for-byte:

* **Topology** — complete binary rooted tree; root `s`, nodes `n1`…`n1022`;
  node `n_k` has parent `n_{(k-1)//2}` (or `s`), and the reach feeding `n_k`
  is `e_{k-1}`.
* **Users** — `f1`…`f500` on terminals `n511`…`n1010`, all of weight 1. The
  12 remaining leaves carry no user, which is why 22 reaches carry no load.
* **Efficiency** — uniform within a period: `η(k_j) = (100 − j)/100`, i.e.
  0.99, 0.98, 0.97, 0.96.
* **Demand** — `d(f_i, k_j) = 20 + ((7i + 11j) mod 31)`, an integer in
  [20, 50]; the coprime strides 7 and 11 against the modulus 31 spread the
  demands over the tree and over time deterministically.
* **Reach capacity** — `6/5 · L(e, k)` for every loaded reach, and 1 for the
  22 reaches with no user downstream.
* **Source capacity** — `(10 − j)/10 · L(s, k_j)`, so period `k4` is the
  Stage-1 bottleneck and the closed-form optimum is 3/5.

Because every reach is slack by construction, **this instance says nothing
about capacity-limited behaviour** and is never used for that purpose; it is
a timing and scale benchmark (Section 4.7 and Table 7). The capacity
structure that is deliberately *not* tied to the loads is the one used by the
independent-capacity families of Section 4.10.

## Reproducing and checking

```bash
# verify both imposed-parameter rules (also run by the test suite)
python Data/design/build_gone_abat_jap_capacities.py
python Data/design/build_synthetic_scale.py

# print the Gone Abat Jap capacity / load / ratio table
python Data/design/build_gone_abat_jap_capacities.py --table

# regenerate the files from their rules
python Data/design/build_gone_abat_jap_capacities.py --write
python Data/design/build_synthetic_scale.py --write

# run the provenance tests only
pytest tests/test_data_provenance.py -v
```

SHA-256 checksums of every file in this folder, together with those of every
generated result, are recorded in `results/manifests/run_manifest.json`.
